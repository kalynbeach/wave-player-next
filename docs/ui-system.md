## Decision

Use shadcn/ui for the React component layer and begin with the user-selected Base UI preset.

Use the card-centered interaction model in [Player Card Interface](player-card-interface.md) as the initial application shell. The player is one composed card with internal semantic regions, not a dashboard made from many cards.

Preset builder:

- [Wave Player Next shadcn/ui preset](https://ui.shadcn.com/create?preset=b1D0enCq&base=base&pointer=true)

Preset code:

- `b1D0enCq`

User-provided apply command:

```bash
bunx --bun shadcn@latest apply --preset b1D0enCq
```

This command was applied in the Wave Player Next repository during Task 1. The resulting project uses Base UI primitives and the decoded preset below.

## Base UI requirement

Base UI is an intentional architectural choice for the initial component layer.

Consequences:

- use Base UI component APIs generated by shadcn;
- use Base UI's `render` composition pattern where a custom trigger or element is needed;
- do not copy Radix-specific `asChild` usage into Base UI components;
- verify component documentation against the configured primitive base before implementation;
- treat a base change as an explicit migration, not a casual preset update.

## Applied Task 1 setup procedure

1. Create the Bun/React project.
2. Initialize shadcn/ui with Base UI primitives.
3. Confirm `components.json` and `bunx --bun shadcn@latest info --json` report `base: base`.
4. Apply preset `b1D0enCq` with the user-provided command.
5. Decode or resolve the preset again and compare the effective configuration.
6. Review every created or modified file.
7. Commit only after the app builds, type-checks, and the relevant tests pass.

Do not run a preset blindly over locally customized components later. Inspect the existing preset, preview changes, and choose an overwrite, partial, merge, or skip strategy.

## Component policy

Use existing shadcn components before creating bespoke styled markup. Add only components required by the current vertical slice.

Likely early components:

- `Button` for transport actions;
- `Slider` for volume, seeking, and scene parameters;
- `ToggleGroup` for oscilloscope/Lissajous mode selection;
- `ScrollArea` for the library;
- `Tooltip` for compact transport and visualizer controls;
- `DropdownMenu` or `ContextMenu` for track actions;
- `Dialog` for focused settings when inline card presentation is insufficient;
- `Tabs` or a single-select `ToggleGroup` for card view switching;
- `Empty` for an unconfigured or empty library;
- `Skeleton` for loading;
- `Alert` for scan, playback, and capability errors;
- `Separator` for structural division;
- `Badge` for format, version, availability, or analysis status;
- `Command` for later library search and command access.

Do not install every component preemptively.

## Custom surfaces

shadcn/ui should own controls, layout primitives, overlays, feedback, and accessible interaction patterns.

It should not replace specialized product surfaces:

- the WebGPU visualizer canvas;
- waveform or spectrum rendering;
- artwork and media-specific composition;
- transport and library controllers;
- audio analysis logic.

These surfaces should compose with shadcn components and semantic tokens rather than be forced into generic cards.

The outer player may use shadcn's full `Card` composition. Track identity, the central viewport, and transport are its internal regions; they must not each become nested cards. Use semantic elements, layout, and `Separator` when separation is needed.

## Theming relationship

The preset establishes the initial component implementation and default semantic token system. It does not define the final limits of user-selectable themes.

Rules:

- use semantic CSS variables and token names;
- avoid hard-coded raw color utilities in product components;
- keep shadcn component source inside the project and review customizations;
- define runtime themes as data that changes semantic tokens;
- keep scene rendering palettes distinct from UI tokens while allowing intentional linkage;
- preserve the no-radius starting character unless a later theme explicitly changes it;
- use the configured Phosphor icon library rather than assuming Lucide.

Task 1 adds one small Wave-specific semantic layer in the configured global Tailwind CSS file for the player frame, internal section, visualization background, signal channels, meter, and active transport state. This layer is required for product identity and future themes; it must not duplicate the entire shadcn token system.

## Composition rules

- Use `FieldGroup` and `Field` for forms.
- Use `ToggleGroup` for small option sets instead of manually styled buttons.
- Keep menu items inside their required groups.
- Provide titles for dialogs, sheets, and drawers, including visually hidden titles when necessary.
- Use full card composition where cards are actually appropriate.
- Use `Empty`, `Alert`, `Skeleton`, `Separator`, and `Badge` rather than recreating them.
- Use `gap-*` layout rather than `space-x-*` or `space-y-*`.
- Use component variants and semantic tokens before custom styling.
- Use `data-icon` conventions and let components size icons.

## Accessibility

The player must remain usable without the visualizer.

Requirements:

- every transport action has an unambiguous accessible name;
- sliders expose labels, values, ranges, and keyboard behavior;
- repeated track and scene actions include track/scene context in their accessible names;
- visual mode controls expose selected state;
- visualizer canvas has a useful label and textual status;
- reduced-motion preferences affect nonessential UI animation;
- frequent transport and keyboard actions are never delayed by decorative animation;
- focus remains visible in custom themes;
- color is not the only signal for playback, errors, or availability;
- library browsing and playback remain keyboard accessible.

## Testing implications

Use `bun test` with React Testing Library and Happy DOM for component behavior, semantics, and accessibility-oriented queries. Base UI behavior that depends on real layout, pointer capture, browser media, or GPU rendering requires Codex-native live browser verification.

The implementation task must use:

- Impeccable for product/design context, shaping, and audit passes;
- shadcn guidance for Base UI component selection and composition;
- Interface Craft for screenshot critique, animation storyboards, and optional development-only DialKit tuning;
- Emil Kowalski's design-engineering guidance for timing, easing, interruption, transform origins, and perceived performance;
- the Codex in-app Browser for the running localhost interface;
- Computer Use only where native macOS or browser-chrome interaction is not adequately available through the Browser plugin.

References:

## Settled initial composition

- one responsive portrait player card is the primary application shell;
- track identity and transport remain persistent;
- visual, library, and scene controls are changeable internal views;
- the visualization is the default and dominant view;
- narrow layouts preserve the same card anatomy rather than adding a sidebar;
- Task 1 uses one theme based on the preset plus Wave-specific semantic tokens;
- Work grouping presentation remains a Phase 2A design decision.

Exact measurements, typography, colors, and transition curves are implementation-tuning decisions to resolve against the live interface with the installed design skills. They do not block the first goal.
